# Shipment ETA & Delay Propagation

**Aiqon AI Internship: Round 2 take-home** · Sridhar Mukkandi

A system that predicts a shipment's final delivery time, the probability and size of its delay, and **why**. It names the stage and the factors behind the delay and shows how lateness in one stage spreads into the next.

📦 **Repo:** https://github.com/Mukkandi-Sridhar/shipment-eta-propagation · 📄 **Report:** [`docs/Report.pdf`](docs/Report.pdf) · 🖥️ **Dashboard:** `make serve` → http://localhost:8000

---

## The idea in one paragraph

A shipment is a chain of five stages: **origin → ocean → destination port → customs → last mile**. The five stage overruns (actual minus scheduled duration) add up exactly to the delivery delay. So I train **one gradient-boosted model per stage** that predicts its overrun from *how late the shipment enters the stage* plus *what is observable at prediction time*, and then **chain** them. Predicted lateness out of one stage feeds the next, so delay is **amplified** when it breaks a buffer (missed berth window, transshipment connection, weekend customs closure, rail cut-off) and **absorbed** when slack exists (speed recovery at sea, early release waiting for a booked truck). Monte-Carlo sampling through the chain gives P10/P50/P90 ETAs and P(late). Explanations are **exactly additive**: observed delay + on-time reference + knock-on + factor SHAP = forecast. Because the data comes from a mechanistic simulator, the explanations are **scored against ground-truth causes**.

## Results (temporal hold-out, 90 unseen shipments)

| MAE (hours) | Booked | Departed | Arrived | Discharged | Released |
|---|---:|---:|---:|---:|---:|
| Carrier schedule | 34.9 | 34.9 | 34.9 | 34.9 | 34.9 |
| Carry-forward lateness | 34.9 | 32.3 | 31.2 | 28.5 | 20.0 |
| Lane history | 38.9 | 37.7 | 34.6 | 31.0 | 19.2 |
| Direct GBM (no stage structure) | 32.6 | 30.6 | 28.1 | 26.5 | 16.0 |
| **Stage-chain (this work)** | 33.8 | 30.7 | **25.9** | **23.5** | **10.1** |

* Late-risk AUC 0.82 at vessel arrival, 0.98 after customs release.
* The stage the model blames is the **true root-cause stage 52%** of the time after departure (lane history 12%, chance 25%).
* At booking no method does much better than the schedule: most delay is still in the future. The report explains why and lists the other limitations.

The exact numbers are regenerated by `make data` and written into `web/public/data/summary.json` and the report.

## Run it

Requirements: Python ≥ 3.11 and Node ≥ 18. Node is only needed to rebuild the UI, because `web/dist` is committed.

```bash
git clone https://github.com/Mukkandi-Sridhar/shipment-eta-propagation.git && cd shipment-eta-propagation
make setup     # venv + pip install -r requirements.txt + npm install
make data      # simulate 300 journeys → train → evaluate → export (~5 min)
make serve     # FastAPI + dashboard on http://localhost:8000  (live what-if works here)
```

Other targets: `make web` (rebuild the UI), `make dev` (hot-reload UI on :5173, proxies `/api` to :8000), `make report` (re-render the PDF). Without `make`:

```bash
python -m venv .venv && .venv/bin/pip install -r requirements.txt
.venv/bin/python -m eta.run           # add --fast to skip the learning curve
.venv/bin/python -m eta.report        # docs/report.html + docs/Report.pdf
.venv/bin/uvicorn api.main:app --port 8000
```

## Key assumptions

* **Synthetic data**, built so it has known causes. Public AIS data has no door-to-door milestones and no root-cause labels. Parameters are plausible, not fitted.
* **ETA** = promised delivery + P50 predicted delay. **Late** = more than 24h after the promise.
* Forecasts use only information **reported by the checkpoint**: congestion and weather as observed then, never their realised future values.
* Milestone feeds have gaps (3–20% per event type). Delivery (POD) is always reported.

See the report for the full list and for what would change in production.
